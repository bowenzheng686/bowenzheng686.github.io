# 14 常见面试题

本篇把前十三篇中分散的概念放回实际问题：先判断 Redis 能否解决业务需求，再解释持久化、排障和高可用的取舍。回答时不必背“标准话术”，应说清**前提、机制、边界与验证办法**。

## 场景与数据模型

### 1. Redis 适合做什么？什么时候不该只用 Redis？

Redis 适合需要低延迟访问的数据，例如可失效缓存、会话、限流计数器、排行榜和轻量队列。选型先问：数据能否从权威数据源重建？允许多大丢失窗口？是否需要复杂查询、长期保存和多记录事务？缓存可以容忍失效后回源，但订单或账本不能仅因 Redis 很快就把它当作唯一可靠存储。还要计算内存、持久化和副本成本，而不是只看平均响应时间。

### 2. 常用数据类型与消息队列如何选？

String 可放计数、序列化值；Hash 适合对象字段；List 可做简单队列；Set 用于去重与集合关系；Sorted Set 适合有序排行；Stream 提供消息 ID、消费组、待确认消息等能力。发布订阅只把消息发给当时在线的订阅者，不能替代可靠队列。List 的阻塞弹出比轮询好，但复杂确认、重试与消费组需求通常选 Stream 或专门消息系统。即使使用 Stream，也要设计消费者异常后的 `XPENDING`／`XAUTOCLAIM`、幂等处理和修剪策略。

### 3. Redis 中的数据最终怎样存储？

键值驻留在内存中，数据类型各有内部编码，具体编码受 Redis 版本和数据规模影响。过期时间由过期字典管理，删除结合惰性与定期策略；内存到达 `maxmemory` 后如何处理取决于淘汰策略。RDB/AOF 是磁盘持久化，不意味着每次写入都同步落盘；副本也是异步复制，不应把“有副本”误认作零数据丢失。

## 性能与故障排查

### 4. Pipeline 为什么能提高吞吐？

Pipeline 在不等待每条响应的情况下连续发送多条命令，减少网络往返等待。它不保证一组命令原子执行，也不会把每条命令的服务器 CPU 开销消除。控制批次大小，避免过大的客户端或服务端缓冲、长时间占用连接以及失败后难以界定重试范围；需要原子性时选择事务或 Lua，并评估阻塞时间。

### 5. 客户端超时突然增多，先查什么？

先区分**连接超时、命令读写超时、连接池等待超时**及特定命令的超时，再对齐故障时间线：应用错误率、Redis 延迟、CPU/内存、网络丢包、连接数、慢日志、持久化 fork、主从同步与故障转移事件。若只在少量键或命令上出现，排查大键、热点键和耗时命令；若全体客户端同一时间受影响，先看节点资源、网络和故障切换。不要只调高超时时间掩盖瓶颈；超时重试还可能放大负载或重复写入，应配合退避和幂等性。

### 6. 本机客户端连远端 Redis 失败，有哪些常见原因？

按顺序核对目标地址与端口、DNS/路由、防火墙和安全组、服务监听地址、TLS 与明文是否匹配、ACL 用户及密码、最大连接数、保护模式，再看服务日志。`Connection refused` 多与监听或拒绝连接有关；超时可能是网络丢包或资源耗尽；`NOAUTH`／`WRONGPASS` 指向认证；Cluster 模式下只连一个不可达的重定向目标，也会表现为请求失败。不要为了排障直接把实例开放到所有网络或关闭认证。

### 7. 大键和热键会造成什么影响？

大键占内存、延长删除或序列化时间、拖慢复制与迁移，并可能造成网络输出缓冲增长。热键即单键 QPS 很高，会把某个主节点的 CPU 和带宽用满，影响同节点其他客户端。大键看键大小与操作成本，热键看请求分布；二者可能同时存在，但处理方式不同。大键可拆分、异步删除、改变数据模型；热键可用本地缓存、请求合并、分片键或业务限流，须考虑一致性和计数语义。

### 8. 应监控哪些 Redis 指标？

无论用 Zabbix、Prometheus 还是其他系统，都应覆盖可用性与延迟、连接数及拒绝连接、命中率、QPS/命令分布、内存和碎片率、逐出与过期、慢日志、RDB/AOF 状态、复制偏移与延迟、主从角色变化。Cluster 再加槽位覆盖、故障节点、每主节点资源及热点；Sentinel 还看主节点发现、故障转移和 quorum。告警阈值应参照业务基线与容量计划，单看 `PING` 成功并不足以证明业务可用。

## 持久化与容器

### 9. RDB 与 AOF 的差别是什么？

RDB 在特定时点保存数据快照，文件紧凑、恢复通常较快，但两次快照之间的写入可能丢失，生成快照会带来 fork 与写时复制开销。AOF 记录写命令，`appendfsync` 策略决定持久化频率、性能与可能的数据丢失窗口；重写可缩小文件，但同样要留出额外磁盘和内存余量。两者可以并用，恢复时以实际 Redis 版本和配置规则为准。它们都不能代替异地备份与恢复演练。

### 10. 容器里运行 Redis，怎样保证数据不随容器删除？

把 Redis 的数据目录挂载到持久卷，启用适合业务的 RDB/AOF，把配置和密钥独立管理，并校验容器用户对卷的读写权限。容器重建前后检查数据文件、启动日志、键与 TTL；还需把备份放在**不同故障域**，因为卷本身也可能丢失。仅 `docker run` 启动而未配置卷，不能把容器文件系统当作可靠持久化方案。

## 复制、高可用与分片

### 11. 单机、主从、Sentinel、Cluster 分别解决什么问题？

单机最简单，但容量、写入吞吐和可用性都受单节点限制。主从提供数据副本和可选读扩展，故障后若无协调机制仍须人工切换。Sentinel 监控并选出新主节点、通知客户端，仍是单主写入。Cluster 通过多个主节点分片，同时支持对应副本的故障转移，代价是客户端、跨键操作和运维更复杂。应先明确是要解决可用性还是容量与吞吐，再决定架构。

### 12. 主从复制大致怎样工作？

副本建立连接并请求同步；能接续复制积压缓冲区时可做增量同步，否则需要全量同步与后续命令流。复制过程是异步的，故障时副本可能落后主节点；应监控连接状态、偏移量、复制延迟和缓冲区压力。主节点写入返回成功不等于副本已经保存；`WAIT` 可以等待一定数量副本确认收到写入，但也不是磁盘持久化或强一致事务保证。

### 13. Sentinel 怎样判断故障并切换？

Sentinel 的单点超时判断是主观下线；满足配置的 `quorum` 才形成客观下线。后续还须选出负责故障转移的 Sentinel 并取得足够授权，挑选合格副本升主、重配其他副本，再让支持 Sentinel 的客户端重新发现主节点。`quorum` 不等于最终授权所需多数；网络分区或副本滞后仍可能造成中断与数据丢失。

### 14. Cluster 的键如何分布、客户端怎样找到节点？

共有 **16,384** 个槽，通常按 `CRC16(key) mod 16384` 定位；若键含合法 hash tag，则使用标签中的内容计算。每个槽在某一时刻由一个主节点负责，副本复制它的数据。客户端缓存槽到节点的映射，遇到 `MOVED` 更新路由；迁槽期间按 `ASK` 临时请求目标节点。能连接种子节点不代表所有重定向目标都可达，因此还要检查节点发布的地址。

### 15. 为什么常见三主三从？“最少几个节点”怎样回答？

三主节点是典型起点，可形成持槽主节点多数；给每个主节点配一副本，便形成常见的六实例高可用布局。这里的“最少”取决于要达成的目标：创建能分片的集群、容忍一个主节点故障、跨故障域部署是不同要求。三主三从也不能保证任意多个节点故障都可用；如果主副本落在同一宿主机，六实例仍可能被一次宿主机故障击穿。

### 16. 缺一个槽位或一个主节点，会怎样？

若某槽无人负责，访问该槽的键一定失败。默认 `cluster-require-full-coverage yes` 时，槽位不完整还可能让整个集群进入失败状态；设为 `no` 可让有覆盖的槽继续服务，但应用必须接受部分键不可达。还要判断剩余主节点能否形成多数、故障主节点是否有合格副本。不能简单说“主节点剩一半就能继续用”。

### 17. 如何理解“脑裂”，怎样降低风险？

网络分区可能让不同侧对主节点状态认知不同；故障转移后，旧主节点上的未复制写入可能丢失。Cluster 通过主节点多数参与故障判定与副本选举限制分区中任意升主，但异步复制仍有数据丢失窗口。把主副本放在不同故障域，正确设置 `min-replicas-to-write`／`min-replicas-max-lag` 等可降低风险，不能承诺绝对零丢失；对关键写入还需业务幂等、权威存储或更强一致性的方案。

### 18. 为什么某个 Cluster 节点内存明显更高？

先比较槽数、键数、平均值大小、大键、过期分布、客户端输出缓冲、复制缓冲和内存碎片。相同槽数不保证数据量相同。若是槽位分配不均，可在容量与业务低峰条件下迁槽或 `rebalance`；若是一个热点键或大键，单纯平衡槽数通常无效，要改数据模型或访问模式。

### 19. 多键命令、读副本与逻辑数据库有哪些限制？

Cluster 只支持 DB 0；跨槽的多键命令、事务和脚本会报 `CROSSSLOT` 或无法保证所需原子性。合理使用 hash tag 让相关键同槽，但别把所有键塞进一个槽。副本默认把普通请求重定向到主节点；客户端可对副本连接发送 `READONLY` 读取其负责槽的数据，但可能读到复制延迟的数据，并须在拓扑变化后更新路由。

## 一道综合题：怎样选择并验证部署模式？

先列数据量、峰值 QPS、写入比例、延迟目标、可容忍丢失窗口与故障域，再估算单主节点能否承担。如果能承担且只需自动切换，考虑主从加 Sentinel；若需要横向分片，考虑 Cluster 并审视跨键操作与客户端兼容性。无论哪种模式，都要用故障演练验证**客户端恢复、数据正确性、持久化恢复和监控告警**，而不是只看集群命令显示 `ok`。
