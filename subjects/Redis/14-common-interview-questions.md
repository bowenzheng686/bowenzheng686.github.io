# 14 常见面试题

这些问题按“使用场景 → 性能与故障 → 数据与持久化 → 高可用与集群”排列。回答时先说机制，再说适用条件和排查证据，不要把缓存、消息队列和持久化数据库混为一谈。

## 1 使用场景与数据类型

**Redis 适合解决什么问题？** Redis 是以内存为主的键值数据库，常用来做缓存、会话、计数器、排行榜、限流和轻量消息处理。需要考虑内存成本、数据持久化要求、过期策略，以及缓存与源数据库的一致性。

**常用数据类型如何选？** String 适合标量与计数；Hash 适合对象字段；List 适合有序、可从两端操作的数据；Set 适合去重与集合运算；Sorted Set 适合带分数的排行。Stream 适合需要消费组和消息确认的场景。具体选择取决于读写模式，而不是只看数据名称。

**Redis 如何实现消息队列？** List 的阻塞弹出能实现简单队列，Pub/Sub 适合实时广播但不保留离线消息；Stream 支持持久化消息、消费组和待确认列表。它们的可靠性语义不同，不能互换。对强事务、复杂重试与跨系统保证有要求时，应评估专用消息系统。

## 2 性能、监控与故障排查

**Pipeline 为什么能提高吞吐？** 客户端把多条命令批量发送，减少网络往返次数；服务端仍按命令执行。批量过大又会增加响应缓存、内存占用和其他请求的等待时间，因此应分批压测，并结合业务延迟选择批次大小。

**客户端 timeout 突然增多，如何定位？** 先分清连接超时、读取超时和连接池等待超时，再沿客户端、网络、Redis 服务端三个层面排查：检查连接池与线程阻塞、网络丢包和 RTT、CPU/内存与交换、慢查询、持久化和主从同步、超大键及热键。把报错时间与 Redis 指标、日志对齐，避免仅凭一次 `PING` 断定服务正常。

**本地客户端访问远端 Redis 失败有哪些常见原因？** 地址或端口错误、DNS/路由/防火墙不通、Redis 只监听本地地址、认证或 ACL 不匹配、TLS 配置不一致、连接数限制，以及 Cluster 客户端未正确处理重定向。先确认 TCP 连通性和服务端监听，再检查协议与身份验证。

**大 key 和热 key 有什么影响？** 大 key 的序列化、网络传输、删除和迁移会放大延迟及内存峰值；热 key 把请求集中到一个主节点，可能耗尽该节点 CPU 或带宽，进而拖慢同节点的其他客户端。用 `MEMORY USAGE`、`SLOWLOG`、`INFO`、采样或业务侧请求统计定位，再结合拆分、分片、局部缓存和请求合并处理。

**应该监控哪些指标？** 至少关注可用性与错误、命令延迟、每秒操作数、连接数及拒绝连接、内存及淘汰、过期、持久化状态、复制偏移/延迟、主从角色、Cluster 槽位状态和节点间通信。Zabbix、Prometheus 等工具只是采集与告警手段，阈值需要按实例基线确定。

## 3 持久化与复制

**RDB 与 AOF 如何取舍？** RDB 在特定时间点生成快照，文件紧凑、恢复通常较快，但两次快照间的写入可能丢失；AOF 记录写命令，丢失窗口取决于刷盘策略，恢复和文件维护成本也不同。Redis 新版本可能采用多部分 AOF。选型要明确可容忍的数据丢失窗口、恢复时间和磁盘预算，必要时组合使用；复制不是备份。

**Docker 容器中的 Redis 如何保存数据？** 将 `/data` 挂载到持久化卷，配置 RDB/AOF 和合理的刷盘策略，并在重建容器后验证文件恢复。仅把数据写在容器可写层不能代替持久化与备份。

**主从复制如何工作？** 从节点与主节点建立连接，完成全量或增量同步，然后持续接收复制流。复制默认异步，因此故障切换时可能丢失尚未复制的写入；读副本也可能读到旧数据。应监控复制延迟与偏移，并让业务明确可接受的一致性级别。

## 4 哨兵与 Cluster

**单机、主从、Sentinel 和 Cluster 的区别？** 单机部署简单但缺乏高可用；主从增加读副本但不自动故障切换；Sentinel 监控并选举新主节点，解决主节点故障切换，但写容量仍受单主限制；Cluster 把 16,384 个哈希槽分给多个主节点，以水平分片提高容量和写吞吐，并支持副本故障切换。

**Sentinel 如何选主？** Sentinel 通过心跳判断主观下线，在达到法定票数后认定客观下线；取得领导权的 Sentinel 按副本状态、优先级、复制偏移等条件选择副本并执行切换。部署时要理解法定票数和多数派不是同一个概念。

**Cluster 的最小规模与槽位要求？** 能完成分片的基本形态是三个主节点；生产环境通常为每个主节点配至少一个副本，即三主三从。16,384 个槽必须全部分配且处于可服务状态，集群才具备完整键空间；能否在槽位异常时继续处理部分请求，还取决于 `cluster-require-full-coverage` 等配置。键通过 `CRC16(key) mod 16384` 计算槽位；带 `{...}` 的键以花括号内的标签计算，方便同槽多键操作。

**如何理解“脑裂”？** 网络分区可能让原主节点短时间继续接受写入，而多数派一侧已完成故障切换。恢复后旧主上的未复制写入可能丢失。可以通过合适的副本数量、客户端及时刷新拓扑，以及 `min-replicas-to-write` / `min-replicas-max-lag` 等写入约束缩小风险，但不能把异步复制说成零丢失。

**某节点内存明显高于其他节点，如何排查？** 比较槽位数量与各槽数据量，再看大 key、热写入、键过期分布、复制缓冲区、客户端输出缓冲区和内存碎片。槽位数量均衡不代表内存一定均衡，应在定位数据倾斜后再迁移槽位或调整键设计。
