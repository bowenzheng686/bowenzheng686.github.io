# 第 07 章 · 虚拟化原理

KVM 提供 Linux 内核中的硬件辅助虚拟化能力；QEMU 创建虚拟设备并运行来宾进程；libvirt 管理虚拟机定义与生命周期。理解性能或故障时，可分别追踪 **CPU 指令、内存地址、I/O 请求和网络数据包**，不要把四种路径混成“所有操作都由 hypervisor 转换一次”。

## 7.1 CPU：vCPU 如何运行

宿主机调度器将每台虚拟机的 vCPU 线程调度到物理逻辑 CPU 上；来宾内核又在自己的 vCPU 上调度来宾进程。因此 vCPU 数量、宿主机 CPU 争用和来宾应用线程数属于不同层次。

![物理 CPU 时间在任务和虚拟机之间分配的原理示意]({{ '/subjects/KVM/assets/p146-img01.webp' | relative_url }})

来宾应用发出系统调用时，通常先进入**来宾内核**；它不是每次直接进入宿主内核。只有受控事件（例如敏感指令、设备 I/O 或页表相关事件）才可能发生 VM exit，让控制权进入 KVM/QEMU 处理，再通过 VM entry 返回来宾。

### 历史实现与今天的硬件辅助

- **纯模拟**：模拟器解释或动态翻译来宾指令，可以运行不同指令集的系统，但通常开销较高。
- **早期软件完全虚拟化**：为运行未经修改的来宾，VMM 可以对不适合直接执行的指令序列进行二进制翻译（BT），使它们在受控条件下执行。BT 不是把来宾特权指令原样变为宿主机特权指令后放行。
- **硬件辅助虚拟化**：Intel VT-x、AMD-V/SVM 用处理器控制结构隔离来宾状态，并让特定事件触发 VM exit。它减少了早期软件方案的许多困难，但不保证所有工作负载都接近原生速度。
- **半虚拟化接口**：来宾使用了解虚拟环境的驱动或 hypercall，减少某些操作的模拟开销。现代 KVM 常把硬件辅助 CPU 虚拟化与 VirtIO I/O 半虚拟化同时使用，并非互斥的四选一。

![硬件辅助 CPU 虚拟化中来宾与宿主执行路径的历史示意]({{ '/subjects/KVM/assets/p150-img01.webp' | relative_url }})

“完全虚拟化”指来宾操作系统无需为了基本运行而专门修改，并不表示来宾无法检测到虚拟环境；“半虚拟化”也不表示来宾无法执行任何特权指令。原资料所写固定的性能百分比没有工作负载前提，不宜用于容量规划。性能要结合 CPU steal、VM exit、调度延迟和应用指标实测。

## 7.2 内存：从来宾虚拟地址到宿主物理地址

普通进程使用虚拟地址；在虚拟机中还多出一层：**来宾虚拟地址（GVA）→ 来宾物理地址（GPA）→ 宿主物理地址（HPA）**。前半由来宾页表描述，后半由 VMM 或硬件的二阶段页表管理。来宾以为自己拥有连续物理内存，宿主仍可把这些页映射到不同物理位置。

![来宾与宿主之间的两级地址概念示意]({{ '/subjects/KVM/assets/p151-img02.webp' | relative_url }})

### 影子页表与 EPT/NPT

较早的软件方案中，VMM 根据来宾页表和内存映射维护**影子页表**，让硬件可以从来宾虚拟地址找到宿主物理页。来宾修改页表时，VMM 还需同步影子内容；维护、陷入和 TLB 失效会带来开销。影子页表并非“宿主物理地址到来宾物理地址”的逆向映射。

![影子页表方案的历史示意]({{ '/subjects/KVM/assets/p152-img01.webp' | relative_url }})

Intel EPT、AMD NPT 则由硬件协助完成 GPA→HPA 的第二阶段转换。来宾页表仍负责 GVA→GPA；EPT/NPT 不是取消来宾页表或把所有页表搬到一个“虚拟 MMU”。缺页、权限变更和嵌套页表遍历仍有成本，具体收益取决于负载。

![EPT/NPT 二阶段转换的历史示意]({{ '/subjects/KVM/assets/p153-img01.webp' | relative_url }})

TLB 缓存最近使用的地址翻译，减少重复页表遍历。切换虚拟机时，如果没有标识和失效管理，就可能使用错误的缓存结果；处理器的 VPID/ASID 等机制有助于区分上下文、减少全量刷新。它不是简单给每台虚拟机另建一个独立的“影子 TLB”。来宾和宿主的内存统计、气球回收与大页配置都应分别观察，不能凭单一 `free` 输出判断宿主实际占用。

## 7.3 I/O：模拟、VirtIO 与设备直通

来宾应用的读写先经过**来宾内核和驱动**。设备模型决定请求后续怎样由 QEMU、vhost、宿主内核或物理设备处理；不是每次 I/O 都直接交给宿主物理驱动。

![主机应用、内核驱动与设备的关系（高清重绘）]({{ '/subjects/KVM/assets/p154-img01-redrawn.webp' | relative_url }})

| 方法 | 来宾所见 | 特点与边界 |
| --- | --- | --- |
| 传统设备模拟 | E1000 网卡、IDE/SATA 控制器等熟悉设备 | 兼容性较好，设备寄存器与中断模拟会产生开销 |
| VirtIO | VirtIO 网卡、块设备等 | 来宾需对应驱动；共享队列减少传统设备模拟，仍经过受控的宿主处理路径 |
| 块设备直连 | 宿主某个块设备映射为来宾磁盘 | 与**PCI 设备直通**不同；仍可能由 QEMU 处理 I/O，需保证单写者和数据安全 |
| VFIO/PCI 直通 | 来宾直接使用指定 PCI 设备 | 需 IOMMU、合适的分组和驱动，迁移、共享及宿主使用会受限 |

![VirtIO 前端驱动与宿主后端的历史示意]({{ '/subjects/KVM/assets/p155-img02.webp' | relative_url }})

VirtIO 与硬件辅助 CPU 虚拟化可以并用。设备直通中的 DMA 是设备访问内存的机制，IOMMU 为其提供地址转换与隔离；Intel VT-d、AMD-Vi 等能力不等于任何设备都能安全直通。评估时要看 IOMMU 分组、固件、驱动、重置能力，以及能否接受热迁移限制。原文“所有 VirtIO 只有磁盘和网卡”“固定达到物理机某个百分比”都过于绝对。

## 7.4 网络：从来宾网卡到宿主网络

来宾看到的是虚拟网卡（例如 VirtIO NIC）；QEMU 或 vhost 后端可在宿主创建 TAP 接口，libvirt 常给宿主侧接口取 `vnet0` 一类名称。**来宾并没有另一个同名 `vnet0` 与宿主成对通信**：来宾设备名由来宾系统决定。TAP 工作在以太网帧层，TUN 工作在 IP 包层。

![来宾网卡、宿主 TAP 与虚拟网络的关系（高清重绘）]({{ '/subjects/KVM/assets/p157-img02-redrawn.webp' | relative_url }})

常见连接方式要按“来宾到外部”和“外部主动到来宾”分别判断：

| 模式 | 出站路径 | 外部主动访问 |
| --- | --- | --- |
| 桥接 | 来宾通过宿主网桥进入同一二层网络 | 取决于来宾地址、防火墙和物理网络策略 |
| 路由 | 宿主按路由表转发来宾网段 | 需上游知道返回路由，并允许转发 |
| NAT | 宿主对出站流量改写源地址并跟踪连接 | 通常需显式端口转发或其他入口方案 |
| 隔离网络 | 仅在指定虚拟网络/宿主允许的范围内通信 | 默认不通外部，具体取决于 libvirt 网络定义 |

桥接并非必然让宿主物理网卡“像端口一样直接放入桥”；无线网卡、云主机网络等环境有额外限制。路由模式不等于“仅主机模式”；NAT 出站地址也不一定是公网 IP。

![桥接模式的历史示意]({{ '/subjects/KVM/assets/p158-img01.webp' | relative_url }})
![NAT 模式的历史示意]({{ '/subjects/KVM/assets/p159-img01.webp' | relative_url }})

排障时从来宾 `ip addr` 和默认路由开始，依次检查 TAP、宿主网桥或 libvirt 网络、宿主转发与防火墙、上游路由/DNS；不要看到来宾能 ping 宿主就推断外部链路完整。
