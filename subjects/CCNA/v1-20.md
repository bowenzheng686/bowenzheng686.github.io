<section>


<h3 class="h3" id="ch20lev1sec3">使用 ping 命令隔离问题</h3>


<p class="noindent">有人通过电子邮件、短信或电话留言，请你调查用户的网络问题。你通过 Secure Shell（SSH）登录路由器，执行 <strong>ping</strong> 命令并成功。这个结果能够排除哪些可能原因？又有哪些原因仍可能是问题根源？</p>


<p class="noindent">然后，你向另一个地址执行 <strong>ping</strong>，这一次失败了。同样，这次 <strong>ping</strong> 命令失败说明什么？IPv4 路由的哪些部分仍可能有问题，哪些部分现在可以确定没有问题？</p>


<p class="noindent"><strong>ping</strong> 是最常用的网络故障排查工具之一。<strong>ping</strong> 成功时，确认了 IP 路由工作过程中的许多个别环节，从而排除当前问题的一些可能原因。<strong>ping</strong> 失败时，通常有助于缩小互联网络中根本原因可能所在的位置，进一步隔离问题。</p>


<p class="noindent">本节首先简要解释 ping 的工作方式，随后提供一些建议和分析，说明如何使用 <strong>ping</strong> 命令排除某些因素，从而隔离问题。</p>


<section>


<h4 class="h4" id="ch20lev2sec1">ping 命令基础</h4>


<p class="noindent"><strong>ping</strong> 命令通过向某个 IP 地址发送数据包，并期待该地址的设备返回数据包来测试连通性。命令发送的数据包表达的意思是：“如果你收到这个数据包，而且它是发给你的，请回复。”每当 <strong>ping</strong> 发送一个这样的数据包并收到另一台主机返回的消息时，<strong>ping</strong> 就知道数据包已经从源主机到达目的主机并成功返回。</p>


<p class="noindent">更正式地说，<strong>ping</strong> 使用互联网控制消息协议（ICMP），具体采用 <a id="key_225" href="#ref-gloss_181"><span class="blue">ICMP 回显请求</span></a>和 <a id="key_224" href="#ref-gloss_180"><span class="blue">ICMP 回显应答</span></a>消息。ICMP 还定义许多其他消息，但这两种专门用于 <strong>ping</strong> 等命令进行连通性测试。作为协议，ICMP 不依赖 TCP 或 UDP，也不使用任何应用层协议。它作为三层的一部分工作，是辅助 IP 管理网络功能的控制协议。</p>


<p class="noindent"><a href="#ch20fig01">图 20-1</a> 通过示例展示带 IP 首部的 ICMP 消息。本例中，主机 A 的用户打开命令提示符，执行 <strong>ping 172.16.2.101</strong>，测试到主机 B 的连通性。命令发送一个回显请求并等待（步骤 1）；主机 B 收到消息后返回回显应答（步骤 2）。</p>


<figure class="image-c" id="ch20fig01">


<img src="assets/volume1/part5-chapter20/images/vol1_20fig01.jpg" aria-describedby="a20fig01" alt="展示主机 A ping 172.16.2.101 原理的网络示意图。">

<section>


<h4 class="h4" id="ch20lev2sec2">使用 ping 命令测试时的策略和结果</h4>


<p class="noindent">通常，最先接听用户故障来电的人员（常称客户支持代表，CSR）无法从用户设备上执行 <strong>ping</strong>。某些情况下，指导用户输入正确命令并在机器上点击正确位置并不容易；或者用户恰好不在。作为替代，从不同路由器执行不同的 <strong>ping</strong> 命令可以帮助隔离问题。</p>


<p class="noindent">从路由器而不是出现问题的主机执行 <strong>ping</strong> 的问题在于：任何单条路由器 <strong>ping</strong> 命令，都无法精确复制用户设备上执行 <strong>ping</strong> 的效果。不过，每种不同的 <strong>ping</strong> 命令都能进一步帮助隔离问题。本节关于 <strong>ping</strong> 的余下内容，将讨论如何从路由器命令行界面（CLI）使用各种 <strong>ping</strong> 命令排查 IPv4 路由故障。</p>


<section>


<h5 class="h5" id="ch20lev3sec1">从问题源头附近测试较长路径</h5>


<p class="noindent">大多数问题始于“主机 X 无法与主机 Y 通信”之类的描述。很好的第一步是从 X 向主机 Y 的 IP 地址执行 <strong>ping</strong>。但假设工程师无法访问主机 X，就可以改从最接近 X 的路由器执行 <strong>ping</strong>，通常是充当 X 默认网关的路由器。</p>


<p class="noindent">例如，在<a href="#ch20fig01">图 20-1</a> 中，假设主机 A 的用户向 IT 支持报告了向主机 B 发送数据包的问题。在主机 A 上执行 <strong>ping 172.16.2.101</strong> 是很好的第一步，但 CSR 无法访问主机 A，也联系不到其用户。因此，CSR 通过 Telnet 登录路由器 R1，并从那里 ping 主机 B，如<a href="#exa20_2">例 20-2</a> 所示。</p>

<p class="noindent">首先，花一点时间查看第一条 IOS <strong>ping</strong> 命令的输出。默认情况下，Cisco IOS <strong>ping</strong> 发送五个回显消息，超时时间为 2 秒。如果 2 秒内没有收到回显应答，命令就将该消息判为失败，并列出一个句点。如果在 2 秒内收到成功应答，命令就显示一个感叹号。因此，第一条命令中，第一个回显应答超时，其余四个都在 2 秒内收到匹配的回显应答。</p>


<p class="noindent">顺便一提，示例展示 <strong>ping</strong> 的一种常见且正常的现象：第一条 <strong>ping</strong> 命令最初显示一次失败，随后其余消息都成功。这通常是因为端到端路径中的某台设备缺少 ARP 表项。</p>


<p class="noindent">现在思考故障排查，以及成功的 <strong>ping</strong> 对该互联网络当前行为说明了什么。先从整体看：</p>


<ul class="sq">


<li><p class="bull">R1 能够向主机 B（172.16.2.101）发送 ICMP 回显请求消息。</p></li>


<li><p class="bull">R1 默认以出接口的 IP 地址作为这些消息的源地址，本例为 172.16.4.1。</p></li>


<li><p class="bull">主机 B 能够向 R1 的 IP 地址 172.16.4.1 发送 ICMP 回显应答消息（主机将回显应答发往回显请求的源 IP 地址）。</p></li>


</ul>

<p class="noindent"><a href="#exa20_2">例 20-2</a> 中成功的 <strong>ping</strong> 也要求数据链路层和物理层的各项细节正常工作。WAN 链路必须正常：路由器接口必须为 up/up，这通常表示链路能够传输数据。在 LAN 上，R2 的 LAN 接口必须为 up/up。此外，前面讨论的所有以太网 LAN 相关环节都必须正常，因为 <strong>ping</strong> 确认数据包从 R1 一路到达主机 B 并成功返回。具体包括：</p>


<ul class="sq">


<li><p class="bull">所用交换机接口处于 connected（up/up）状态。</p></li>


<li><p class="bull">端口安全（见《<em>CCNA 200-301 官方认证指南，第 2 卷</em>》第二版）没有过滤 R2 或主机 B 发送的帧。</p></li>


<li><p class="bull">STP 已将正确的端口置于转发状态。</p></li>


</ul>


<p class="noindent"><a href="#exa20_2">例 20-2</a> 中的 <strong>ping 172.16.2.101</strong> 还确认 IP 访问控制列表（ACL）没有过滤这些 ICMP 消息。一个 ACL 包含一组匹配规则和动作：某些匹配的数据包被过滤（丢弃），另一些则正常继续前进。ACL 可以在数据包进入或离开路由器接口时检查它们，因此<a href="#ch20fig04">图 20-4</a> 展示 R1 和 R2 上 ACL 可能过滤（丢弃）ICMP 消息的各个位置。（请注意，R1 上的出站 ACL 不会过滤 R1 自身创建的数据包，因此 R1 上方没有向右的箭头。）</p>

<p class="noindent">最后，R1 上成功的 <strong>ping 172.16.2.101</strong> 也可以用来合理推断 ARP 正常工作，而且交换机 SW2 为 MAC 地址<span id="page_517" data-epub-type="pagebreak"></span>表学到了 MAC 地址。R2 和主机 B 需要知道彼此的 MAC 地址，才能将 IP 数据包封装进以太网帧，这意味着双方都必须有匹配的 ARP 表项。交换机会在 R2 和主机 B 发送 ARP 消息，或发送承载 IP 数据包的帧时，学习它们使用的 MAC 地址。<a href="#ch20fig05">图 20-5</a> 展示这些表中预期包含的信息类型。</p>

</aside>


</figcaption>


</figure>


<p class="noindent">从前几页可以看到，在问题源头附近执行 <strong>ping</strong> 的策略，只要 <strong>ping</strong> 成功，就能排除两台主机之间问题的许多可能根本原因。但这种 <strong>ping</strong> 与在实际主机上执行相同 <strong>ping</strong> 的行为并不完全一致。为弥补邻近路由器上 <strong>ping</strong> 测试的不足，接下来几个示例展示测试两台主机之间路径上其他可能存在问题的部分的策略。</p>


</section>


<section>


<h5 class="h5" id="ch20lev3sec2">使用扩展 ping 测试反向路由</h5>


<p class="noindent">前几页讨论从默认路由器执行 ping，却错过了更全面测试 IP 路由的机会。这些测试检查<a id="key_222" href="#ref-gloss_150"><span class="blue">正向路由</span></a>，即朝向目的地的路由。然而，从默认路由执行 ping 并不会测试返回原始主机的<a id="key_227" href="#ref-gloss_332"><span class="blue">反向路由</span></a>。</p>


<p class="noindent">例如，再看<a href="#ch20fig02">图 20-2</a> 的互联网络，注意反向路由并不指向主机 A 子网中的地址。R1 处理 <strong>ping 172.16.2.101</strong> 时，必须为回显请求选择源 IP 地址，而路由器会选择<em>出接口的 IP 地址</em>。R1 发往主机 B 的回显请求使用源 IP 地址 172.16.4.1（R1 的 G0/0/0 IP 地址），回显应答也返回该地址 172.16.4.1。</p>


<p class="noindent">标准 ping 往往无法测试你需要测试的反向路由。本例中，R1 上标准的 <strong>ping 172.16.2.101</strong> 并不测试路由器能否路由回子网 172.16.1.0/24，而是测试它们到子网 172.16.4.0 的路由。更好的 ping 测试应检查返回主机 A 子网的路由；从 R1 执行<em>扩展 ping</em> 就能做到。扩展 ping 允许 R1 的 <strong>ping</strong> 使用 R1 位于子网 172.16.1.0/24 中的 LAN IP 地址，这样回显应答就会流向主机 A 的子网，如<a href="#ch20fig06">图 20-6</a> 所示。</p>


<span id="page_518" data-epub-type="pagebreak"></span>


<figure class="image-c" id="ch20fig06">

<h5 class="h5" id="ch20lev3sec3">使用标准 ping 测试 LAN 邻居</h5>


<p class="noindent">对 LAN 上另一台设备执行 <strong>ping</strong>，能够迅速确认 LAN 是否可以传送数据包和帧。具体来说，成功的 <strong>ping</strong> 能排除许多可能的根本原因。例如，<a href="#ch20fig07">图 20-7</a> 展示 R1 执行 <strong>ping 172.16.1.51</strong> 时产生的 ICMP 消息，它测试的是与 R1 位于同一 VLAN 的主机 A。</p>


<figure class="image-c" id="ch20fig07">


<img src="assets/volume1/part5-chapter20/images/vol1_20fig07.jpg" aria-describedby="a20fig07" alt="展示测试期间发送和接收 ping 过程的示意图。">


<figcaption>


<p class="title-f"><strong>图 20-7</strong> <em>标准 <span class="font"><strong>ping</strong></span> 命令确认 LAN 正常工作</em></p>


<aside class="hidden" id="a20fig07">


<p>子网 172.16.1.0/24 上 IP 地址为 172.16.1.51 的主机 A，在收到回显请求后，向 IP 地址为 .1 的路由器 R1 发送回显应答。主机上方说明目的地确认位于同一子网。R1 向 172.16.1.51 发送 ping。回显应答确认局域网（LAN）正常工作。</p>


</aside>


</figcaption>


</figure>


<p class="noindent">如果 ping 成功，就能确认以下事项，从而排除部分潜在问题：</p>


<ul class="sq">


<li><p class="bull">地址为 172.16.1.51 的主机作出了应答。</p></li>


<li><p class="bull">LAN 能在 R1 与主机 172.16.1.51 之间双向传送单播帧。</p></li>


<li><p class="bull">可以合理推断交换机已学到路由器和主机的 MAC 地址，并将其加入 MAC 地址表。</p></li>


<li><p class="bull">主机 A 和路由器 R1 完成了 ARP 过程，在各自的地址解析协议（ARP）表中列出了对方。</p></li>


</ul>


<p class="noindent"><span id="page_520" data-epub-type="pagebreak"></span>即使两台设备位于同一子网，ping 失败仍可能指向各种问题，例如以下列表中的问题。如果 R1 上的 <strong>ping 172.16.1.51</strong> 失败（见<a href="#ch20fig07">图 20-7</a>），该结果指向以下潜在根本原因：</p>


<ul class="sq">


<li><p class="bull"><strong>IP 编址问题：</strong>主机 A 或路由器可能配置了错误的 IP 地址。</p></li>


<li><p class="bull"><strong>IP 掩码问题：</strong>主机或路由器使用错误子网掩码，会改变其对直连子网地址范围的计算结果，从而影响转发逻辑。例如，主机地址为 172.16.1.51，却使用错误掩码 255.255.255.240，就会认为路由器地址 172.16.1.1 位于另一个子网。</p></li>


<li><p class="bull"><strong>DHCP 问题：</strong>如果使用动态主机配置协议（DHCP），可能存在许多问题。<a href="v1-19.html#ch19">第 19 章</a>“<a href="v1-19.html#ch19">主机上的 IP 编址</a>”对此进行了较深入的讨论。</p></li>


<li><p class="bull"><strong>VLAN 中继问题：</strong>路由器可能配置了 802.1Q 中继，而交换机没有配置，或者相反。</p></li>


<li><p class="bull"><strong>LAN 问题：</strong>二层交换机可能存在多种问题，阻止任何帧在主机 A 与路由器之间流动。</p></li>


</ul>


<p class="noindent">因此，无论 ping 成功还是失败，仅从路由器 ping LAN 主机就有助于进一步隔离问题。</p>


</section>


<section>


<h5 class="h5" id="ch20lev3sec4">使用扩展 ping 测试 LAN 邻居</h5>


<p class="noindent">从路由器对 LAN 主机执行标准 ping，并不测试主机的默认路由器设置，但扩展 ping 可以。两种测试都很有用，尤其有助于隔离问题，因为：</p>


<ul class="sq">


<li><p class="bull">如果对本地 LAN 主机的标准 ping 成功……</p></li>


<li><p class="bull">但对同一 LAN 主机的扩展 ping 失败……</p></li>


<li><p class="bull">问题很可能以某种方式与主机的默认路由器设置有关。</p></li>


</ul>


<p class="noindent">要理解标准和扩展 ping 结果为何具有不同意义，先看前面<a href="#ch20fig07">图 20-7</a> 中 R1 的标准 <strong>ping 172.16.1.51</strong>。作为标准 <strong>ping</strong>，R1 使用 LAN 接口 IP 地址 172.16.1.1 作为 ICMP 回显请求的源地址。因此，主机 A 返回 ICMP 回显应答时，认为目的地址 172.16.1.1 位于同一子网。即使主机 A 完全没有默认路由器设置，发回 172.16.1.1 的 ICMP 回显应答仍能成功！</p>


<p class="noindent">相比之下，<a href="#ch20fig08">图 20-8</a> 展示在 R1 上使用扩展 ping 的不同之处。本地路由器 R1 执行扩展 ping，使用其 WAN IP 地址 172.16.4.1 作为 ICMP 回显请求的源地址，这意味着主机 A 的 ICMP 回显应答将发往另一个子网的地址，迫使主机 A 使用默认路由器设置。</p>


<span id="page_521" data-epub-type="pagebreak"></span>


<figure class="image-c" id="ch20fig08">


<img src="assets/volume1/part5-chapter20/images/vol1_20fig08.jpg" aria-describedby="a20fig08" alt="展示测试期间发送和接收 ping 过程的示意图。">


<figcaption>

<h5 class="h5" id="ch20lev3sec5">使用标准 ping 测试 WAN 邻居</h5>


<p class="noindent">与跨 LAN 的标准 ping 测试一样，通过串行或以太网 WAN 链路在路由器之间进行标准 ping，可以测试链路是否能够传送 IPv4 数据包。在合理设计的 IPv4 编址方案中，同一串行或以太网 WAN 链路上的两台路由器，其 IP 地址应属于同一子网。从一台路由器 ping 另一台的 IP 地址，确认 IP 数据包能够通过链路往返，如<a href="#ch20fig09">图 20-9</a> 中 R1 上的 <strong>ping 172.16.4.2</strong> 所示。</p>

</aside>


</figcaption>


</figure>

<ul class="sq">


<li><p class="bull">两台路由器的 WAN 接口都处于 up/up 状态。</p></li>


<li><p class="bull">链路的第一层和第二层功能正常。</p></li>

<li><p class="bull">远程路由器配置了预期 IP 地址（本例为 172.16.4.2）。</p></li>


</ul>


<p class="noindent">ping 相邻路由器并不测试其他许多功能。不过，虽然测试范围有限，却可以排除 WAN 链路存在第一层或第二层问题，并排除某些基本的三层编址问题。</p>

<section>


<h4 class="h4" id="ch20lev2sec3"><span id="page_522" data-epub-type="pagebreak"></span>使用名称和 IP 地址进行 ping</h4>


<p class="noindent">本章迄今所有示例都是 ping IP 地址。不过，<strong>ping</strong> 可以使用<a id="key_223" href="#ref-gloss_175"><span class="blue">主机名</span></a>，ping 主机名允许网络工程师进一步测试域名系统（<a id="key_220" href="#ref-gloss_108"><span class="blue">DNS</span></a>）过程是否正常工作。</p>


<p class="noindent">首先，几乎所有 TCP/IP 应用程序都使用主机名而非 IP 地址标识另一台设备。没有人打开浏览器就输入 72.163.4.185，而是输入 <a href="https://www.cisco.com">https://www.cisco.com</a> 这样的网页地址，其中包含主机名 <a href="http://www.cisco.com">www.cisco.com</a>。随后，主机在向特定 IP 地址发送数据之前，必须先请求 DNS 服务器将该主机名解析为对应的 IP 地址。</p>


<p class="noindent">例如，在本章多个示例所用的小型互联网络中，主机 A 上的 <strong>ping B</strong> 会测试 A 的 DNS 设置，如<a href="#ch20fig10">图 20-10</a> 所示。当主机 A 发现使用了主机名 B 时，会先查看本地 DNS 名称缓存，确定是否已解析过名称 B。如果没有，主机 A 首先请求 DNS 提供（解析）与名称对应的 IP 地址（图中步骤 1）。只有这样，它才会向主机 B 的 IP 地址 172.16.2.101 发送数据包（步骤 2）。</p>


<figure class="image-c" id="ch20fig10">

<h3 class="h3" id="ch20lev1sec4">使用 traceroute 命令隔离问题</h3>


<p class="noindent">与 <strong>ping</strong> 一样，<strong>traceroute</strong> 帮助网络工程师隔离问题。两者比较如下：</p>


<ul class="sq">


<li><p class="bull">两者都在网络中发送消息以测试连通性。</p></li>


<li><p class="bull">两者都依赖其他设备返回应答。</p></li>


<li><p class="bull">两者都得到多种操作系统的广泛支持。</p></li>


<li><p class="bull">两者都可以使用主机名或 IP 地址标识目的地。</p></li>


<li><p class="bull">在路由器上，两者都有标准版和扩展版，可以更好地测试反向路由。</p></li>


</ul>


<p class="noindent">最大的差异在于，<strong>traceroute</strong> 输出的结果更详细，而生成这些输出也需要 <strong>traceroute</strong> 花费额外时间和工作。接下来这一主要部分研究 traceroute 的工作方式，并提供一些建议，说明如何利用更详细的信息更快隔离 IP 路由问题。</p>


<section>


<h4 class="h4" id="ch20lev2sec4">traceroute 基础</h4>


<p class="noindent">假设某位网络工程师或 CSR 开始排查问题。她从用户主机执行 ping，又从附近路由器执行 ping，几条命令之后，确信主机确实能收发 IP 数据包。问题可能尚未解决，但看起来并不是网络问题。</p>


<p class="noindent">现在假设另一个问题出现，这次 <strong>ping</strong> 失败了。看来 IP 网络中确实存在问题。问题在哪里？工程师应该进一步检查何处？虽然 <strong>ping</strong> 有助于隔离问题来源，但 <strong>traceroute</strong> 可能是更好的选择。<strong>traceroute</strong> 通过展示数据包在被丢弃前能在 IP 网络中走多远，系统地帮助定位路由问题。</p>


<p class="noindent"><strong>traceroute</strong> 标识从源主机到目的主机正向路径上的路由器。具体而言，它列出各条独立路由中每台路由器的下一跳 IP 地址。例如，在<a href="#ch20fig11">图 20-11</a> 的主机 A 上执行 <strong>traceroute 172.16.2.101</strong>，将识别路由器 R1 的一个 IP 地址、R2 的另一个 IP 地址，最后识别主机 B，如图所示。随后<a href="#exa20_6">例 20-6</a> 列出主机 A 上该命令的输出。</p>

<h5 class="h5" id="ch20lev3sec6">traceroute 命令的工作方式</h5>


<p class="noindent"><strong>traceroute</strong> 通过生成会触发路由器错误消息的数据包来收集信息；这些消息标识路由器，使 <strong>traceroute</strong> 能在输出中列出其 IP 地址。该错误消息是 ICMP 生存时间超限（TTL Exceeded）消息，最初用于在数据包陷入网络循环时通知主机。</p>


<p class="noindent">暂时不看 traceroute，转而关注 IP 路由。IPv4 路由器通过丢弃循环的 IP 数据包，部分地解决路由环路问题。为此，IPv4 首部包含名为生存时间（TTL）的字段。创建数据包的原始主机设置初始 TTL 值，随后每台转发数据包的路由器将 TTL 减 1。当某路由器将 TTL 减到 0 时，它就认为数据包正在循环，并丢弃数据包。路由器还会发送 ICMP TTL Exceeded 消息，通知发送该被丢弃数据包的主机。</p>


<p class="noindent">现在回到 traceroute。它发送 TTL 较低的消息，以迫使路由器返回 TTL Exceeded。具体而言，<strong>traceroute</strong> 首先发送若干数据包（通常三个），每个首部的 TTL 字段都为 1。当数据包到达下一台路由器时——在<a href="#ch20fig12">图 20-12</a> 示例中为主机 A 的默认路由器 R1——路由器将 TTL 减到 0 并丢弃数据包，然后向主机 A 发送 TTL Exceeded 消息，为 <strong>traceroute</strong> 标识该路由器的 IP 地址。</p>


<figure class="image-c" id="ch20fig12">


<img src="assets/volume1/part5-chapter20/images/vol1_20fig12.jpg" aria-describedby="a20fig12" alt="展示识别网络路径中第一台路由器的示意图。">


<figcaption>


<p class="title-f"><strong>图 20-12</strong> <em><span class="font"><strong>traceroute</strong></span> 如何识别路径中的第一台路由器</em></p>


<aside class="hidden" id="a20fig12">


<p>主机 A 向 IP 地址为 172.16.1.1 的路由器 R1 发送 TTL 为 1 的 IP 数据包。R1 收到后将 TTL 减 1，结果为 0，因此从源地址 172.16.1.1 向主机 A 返回“TTL Exceeded”消息。</p>


</aside>


</figcaption>


</figure>


<p class="noindent"><span id="page_526" data-epub-type="pagebreak"></span><strong>traceroute</strong> 发送多个 TTL=1 的数据包，并根据 TTL Exceeded 消息的源 IP 地址，检查它们是否来自同一路由器。假设消息来自同一路由器，<strong>traceroute</strong> 就将该 IP 地址列为下一行命令输出。</p>


<p class="noindent">为了找到路径中的所有路由器，并最终确认数据包一路到达目的主机，<strong>traceroute</strong> 先发送一小组 TTL=1 的数据包，再发送一组 TTL=2 的数据包，随后依次为 3、4 等，直到目的主机应答。<a href="#ch20fig13">图 20-13</a> 展示第二组中 TTL=2 的数据包。本例中，一台路由器 R1 实际转发了数据包，而另一台路由器 R2 恰好将 TTL 减为 0，导致向主机 A 返回 TTL Exceeded 消息。</p>


<figure class="image-c" id="ch20fig13">


<img src="assets/volume1/part5-chapter20/images/vol1_20fig13.jpg" aria-describedby="a20fig13" alt="展示 TTL 设为 2 时，traceroute 如何识别路径中路由器的示意图。">


<figcaption>


<p class="title-f"><strong>图 20-13</strong> <em><span class="font"><strong>traceroute</strong></span> 发送的 TTL=2 消息</em></p>


<aside class="hidden" id="a20fig13">


<p>IP 地址为 172.16.1.1 的主机 A 发送 TTL 为 2 的 IP 数据包。数据包首先到达路由器 R1，TTL 减为 1；随后到达第二台路由器 R2，其接口标为 G0/0/1，IP 地址为 172.16.4.2。在这里 TTL 再次递减至 0。R2 向源主机 A 返回“TTL Exceeded”消息。R2 连接 IP 地址为 172.16.2.101 的主机 B。</p>


</aside>


</figcaption>


</figure>


<p class="noindent">图中展示四个步骤：</p>


<ol class="number">


<li><p class="number"><strong>traceroute</strong> 发送第二组中的一个数据包，TTL=2。</p></li>


<li><p class="number">路由器 R1 处理数据包，将 TTL 减为 1，并转发数据包。</p></li>


<li><p class="number">路由器 R2 处理数据包，将 TTL 减为 0，并丢弃数据包。</p></li>


<li><p class="number">R2 通过发送 ICMP TTL Exceeded 消息，通知发送主机数据包已被丢弃。该消息的源 IP 地址为 172.16.4.2。</p></li>


</ol>


<p class="noindent">最后，路由器返回的超时消息选择哪个源 IP 地址，对 <strong>traceroute</strong> 输出影响很大。大多数路由器采用较简单的逻辑，也使 <strong>traceroute</strong> 等命令输出更一致、更有意义：根据被丢弃的原始消息到达的接口，选择 TTL Exceeded 消息的源 IP 地址。在<a href="#ch20fig13">图 20-13</a> 中，步骤 2 的原始消息到达 R2 的 G0/0/1 接口，因此步骤 3 中，R2 使用 G0/0/1 的 IP 地址作为 TTL Exceeded 消息源地址，并通过该接口发送消息。</p>

<p class="noindent">大多数操作系统（包括 Cisco IOS）都有 <strong>ping</strong> 和 <strong>traceroute</strong> 命令。不过，有些操作系统的 <strong>traceroute</strong> 语法略有不同。例如，大多数 Windows 操作系统支持 <strong>tracert</strong> 和 <strong>pathping</strong>，而不是 <strong>traceroute</strong>。Linux 和 OS X 支持 <strong>traceroute</strong> 命令。</p>


<div class="note">


<p class="note-title">注意</p>


<p class="note-para">主机操作系统的 <strong>traceroute</strong> 通常创建 ICMP 回显请求，而 Cisco IOS 的 <strong>traceroute</strong> 则创建带 UDP 首部的 IP 数据包。这一点目前看似微不足道，但请注意，ACL 实际上可能过滤主机 <strong>traceroute</strong> 消息的流量，却不过滤路由器 <strong>traceroute</strong> 的流量，反之亦然。</p>


</div>

<h3 class="h3" id="ch20lev1sec5">Telnet 和 SSH</h3>


<p class="noindent"><strong>ping</strong> 和 <strong>traceroute</strong> 为网络人员提供了两个出色工具，用来开始隔离 IP 路由问题的原因。但这两条命令不会告诉我们各网络设备内部的<span id="page_528" data-epub-type="pagebreak"></span>运行状态。当你通过 <strong>ping</strong> 和 <strong>traceroute</strong> 开始了解问题类型及可能位置后，下一步就是查看各种路由器和交换机功能的状态。一种方法是通过 Telnet 或 Secure Shell（SSH）登录设备。</p>


<section>


<h4 class="h4" id="ch20lev2sec5">使用 IOS Telnet 和 SSH 客户端的常见原因</h4>


<p class="noindent">通常，网络工程师使用 PC、平板电脑或其他用户设备上的 Telnet 或 SSH 客户端登录远程设备。实际上，同一个软件包通常同时支持 Telnet 和 SSH。不过，有时你可能希望利用路由器和交换机 IOS 内置的 Telnet 与 SSH 客户端，从一台 Cisco 设备 Telnet／SSH 到下一台。</p>


<p class="noindent">要理解原因，请看<a href="#ch20fig14">图 20-14</a> 的示例。图中的箭头指向三台不同 Cisco 路由器上的三个不同 IP 地址。PC1 在其 Telnet／SSH 客户端的不同标签页中，尝试 Telnet 到各地址。然而，R2 恰好存在路由协议配置错误，导致 R1、R2 和 R3 无法相互学习路由。因此，PC1 对 10.1.2.2（R2）和 10.1.3.3（R3）的 Telnet 尝试都失败。</p>


<figure class="image-c" id="ch20fig14">


<img src="assets/volume1/part5-chapter20/images/vol1_20fig14.jpg" aria-describedby="a20fig14" alt="展示 Telnet 仅能从 PC1 到 R1 成功通信，无法进一步从 R1 到 R2 或 R3 的情形示意图。">


<figcaption>


<p class="title-f"><strong>图 20-14</strong> <em>PC1 可以 Telnet 到 R1，但无法到达 R2 或 R3</em></p>


<aside class="hidden" id="a20fig14">


<p>网络场景中，IP 地址为 10.1.1.0/24 的主机 PC1 通过 Telnet 连接路由器 R1。然而，从 R1 到 IP 地址为 10.1.2.0/24 的另一台路由器 R2 的 Telnet 连接标有叉号，表示失败。从 R2 到 IP 地址为 10.1.3.0/24 的路由器 R3 的连接也用叉号表示未成功。</p>


</aside>


</figcaption>


</figure>


<p class="noindent">在某些情况下，例如本例，从网络工程师设备发起 Telnet 或 SSH 登录可能失败，但仍可以通过 <strong>telnet</strong> 和 <strong>ssh</strong> 命令使用路由器或交换机上的客户端，找到登录办法。在这个特定场景中，每条独立数据链路都正常，问题出在路由协议交换路由的过程。PC1 可以 ping R1 的 10.1.1.1，R1 可以 ping R2 的 10.1.2.2，R2 可以 ping R3 的 10.1.3.3。由于每条链路正常，而且各路由器都能通过共享数据链路与邻居收发数据包，就可以逐台 Telnet／SSH 到后续设备。</p>


<p class="noindent"><a href="#ch20fig15">图 20-15</a> 展示这一思路。PC1 首先建立到路由器 R1 的 Telnet／SSH 连接，如左侧所示。随后用户在 R1 上执行 <strong>telnet 10.1.2.2</strong>，Telnet 到 R2。登录 R2 后，用户可以在 R2 上执行命令。随后又可以从 R2 执行 <strong>telnet 10.1.3.3</strong>，Telnet 到 R3，并在 R3 上执行命令。</p>


<figure class="image-c" id="ch20fig15">


<img src="assets/volume1/part5-chapter20/images/vol1_20fig15.jpg" aria-describedby="a20fig15" alt="展示连续 Telnet 连接的网络示意图。">


<figcaption>


<p class="title-f"><strong>图 20-15</strong> <em>连续的 Telnet 连接：PC1 到 R1、R1 到 R2，以及 R2 到 R3</em></p>


<aside class="hidden" id="a20fig15">


<p>左侧主机 PC1 发起到路由器 R1 的 Telnet 连接，用箭头表示。R1 有一个到 10.1.2.2 的 Telnet 连接，使用子网 10.1.2.0/24。从 R1 建立到第二台路由器 R2 的另一条 Telnet 连接，也用箭头表示。R2 有一个到 10.1.3.3 的 Telnet 连接，属于子网 10.1.3.0/24。第三条 Telnet 连接从 R2 到 R3，用箭头表示。整个过程说明连续 Telnet 连接的概念：PC1 到 R1、R1 到 R2，以及 R2 到 R3。</p>


</aside>


</figcaption>


</figure>


<p class="noindent"><span id="page_529" data-epub-type="pagebreak"></span><a href="#ch20fig15">图 20-15</a> 中的 Telnet 连接能够工作，是因为每条连接都使用同一子网中的源和目的地址。例如，R1 的 <strong>telnet 10.1.2.2</strong> 当然使用 10.1.2.2 作为目的地址。R1 采用向 10.1.2.2 发送数据包所用出接口的 IP 地址，本例为 10.1.2.1。由于每条 <strong>telnet</strong> 都连接直连子网中的 IP 地址，即使路由协议完全配置错误，你仍可逐台 Telnet／SSH 到后续设备，排查并修复问题。</p>


<p class="noindent">网络工程师有时也只是出于个人偏好而使用 IOS Telnet 和 SSH 客户端。例如，需要登录多台 Cisco 设备时，可以在 PC 上打开多个窗口和标签页，分别从 PC 登录（假设网络没有问题）；也可以从 PC 登录附近某台 Cisco 路由器或交换机，再从那里 Telnet 或 SSH 到其他 Cisco 设备。</p>


</section>

<section id="ref-glossary"><h2 class="h2a">术语表</h2><p class="gloss" id="ref-gloss_108"><strong>DNS</strong> 域名系统。广泛用于互联网的应用层协议，用于将主机名转换为相应的 IP 地址。</p>

<p class="gloss" id="ref-gloss_150"><strong>正向路由（forward route）</strong> 从某台主机的角度看，数据包从该主机到另一台主机所经过的路由。</p>

<p class="gloss" id="ref-gloss_175"><strong>主机名（hostname）</strong> IP 主机的字母数字名称。</p>

<p class="gloss" id="ref-gloss_180"><strong>ICMP 回显应答（ICMP echo reply）</strong> ICMP 消息的一种，专门用于 ping 命令测试网络连通性。ping 首先向另一台主机发送 ICMP 回显请求，然后期待从对方收到此类消息。</p>

<p class="gloss" id="ref-gloss_181"><strong>ICMP 回显请求（ICMP echo request）</strong> ICMP 消息的一种，专门作为 ping 命令测试网络连通性时发送的消息。ping 向其他主机发送这些消息，并期待对方以 ICMP 回显应答响应。</p>

<p class="gloss" id="ref-gloss_332"><strong>反向路由（reverse route）</strong> 从某台主机的角度看，另一台主机发回的数据包所经过的路由。</p>
